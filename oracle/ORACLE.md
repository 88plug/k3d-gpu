# Xeon SLO oracle (prototype)

`slo_oracle.py` predicts an agent workload's task p50/p95 on a Xeon serving pod
and gates a Deployment on the annotation `k3d-gpu.io/xeon-slo-p95`. It needs
four short microbenchmarks run on the target Xeon and an engine-agnostic agent
trace. Python stdlib only.

```sh
python3 oracle/test_slo_oracle.py            # 20 unit tests, < 1 s
python3 oracle/run_sim.py                    # pre-registered grid, ~70 s, writes oracle/sim_results.json
python3 oracle/slo_oracle.py anchors         # microbenchmark shapes to run on the target
python3 oracle/slo_oracle.py gate --trace oracle/examples/trace.react.json \
    --model llama-3.1-8b --anchors oracle/examples/anchors.synthetic.json \
    --manifest oracle/examples/deployment.yaml   # exit 0 PASS / 1 FAIL / 2 INCONCLUSIVE
```

**Status: simulation only. Nothing here has been measured on hardware.**
`examples/anchors.synthetic.json` is generated by the oracle itself, and the
c8i platform card is a labelled placeholder.

## What changed from the original idea, and why

The refuter's objection holds, and the design follows it:

* **Laptop-to-Xeon transfer is dropped.** Factors fitted on a 35 W hybrid CPU
  describe that CPU's kernels and power cap. In the sim, a laptop-only fit
  predicts Xeon task p50 at **286 % MAPE** (C4, predicted to fail, and it
  did). All calibration now happens on the Xeon itself: four anchors, under a
  minute of runtime.
* **The fair baseline is used.** It gets the same Xeon anchors as the oracle.
  TTFT scales with uncached tokens, TPOT is linear in context through both
  decode anchors, and the critical path is replayed.
* **The trace carries structure, not timing.** It holds the DAG, the prompt
  as ordered message segments, output tokens and tool durations. It holds no
  timestamps and no cached-token counts. Concurrency comes out of an
  event-driven replay. Prefix-cache hits are recomputed against the target
  engine's cache size (objection b).
* **Contention is modelled.** An iteration-level continuous-batching
  scheduler runs on top of the roofline: decode first, then chunked prefill
  fills the token budget (objection c). MoE weight traffic per step is the
  expected union of experts touched by the batch.
* **Overlap with the agent-trace bench** (`origin/claude/invent-agent-trace-bench`)
  is avoided. This branch only *predicts*. Capturing and measuring traces is
  that bench's job, and live scoring should use it as the measuring side.

## Mechanism

| Step | What it does |
|---|---|
| Fit | `prefill` (in 4096) TTFT gives the compute efficiency. Batch-1 `decode` TPOT at contexts 256 and 8192 is linear in bytes streamed: the slope gives bandwidth efficiency and the intercept gives the per-step overhead. The held-out `valid` shape (16 concurrent) sets the band: `max(10 %, 2 x residual)`. |
| Replay | Event-driven DAG. Each LLM step enters the batching engine when its dependencies finish. Tool steps take their recorded duration. |
| Step cost | `max(FLOPs / (peak x eff_c), bytes / (bw x eff_b)) + step_s`. Bytes = weights (MoE expert union) + KV read/write. |
| Gate | PASS if `p95 x (1 + band) <= SLO`, FAIL if `p95 x (1 - band) > SLO`, otherwise INCONCLUSIVE. |

## Simulation results (full grid, `sim_results.json`)

Ground truth is `truth_sim.py`, written separately (its own scheduler, cache
and DAG loop). It adds effects the oracle does not model:
- compute-efficiency saturation with an AVX-512 floor;
- bandwidth loss as batch grows;
- imperfect compute/memory overlap;
- slower attention;
- per-sequence sampler cost;
- front-end delay;
- step noise, block-granular cache and tool jitter;
- true peak and bandwidth off the platform card by a factor of 0.7 to 1.3.

All of these are drawn per seed. The grid is 3 models x 3 trace families x 2
loads x 8 seeds = 144 cells. High load means overlapping tasks. In the 8B
react quick runs, mean concurrency (rate x p50) was about 13 to 15 tasks.

| Predictor | task p50 MAPE | task p95 MAPE | p95 MAPE, high load | p95 MAPE, low load |
|---|---|---|---|---|
| **Oracle** | **7.0 %** | **6.9 %** | **12.2 %** | **1.6 %** |
| Fair baseline (same anchors + ratio) | 32.3 | 32.7 | 59.1 | 6.2 |
| Ablation: each call priced solo | 32.1 | 32.4 | 59.0 | 5.9 |
| Ablation: laptop-recorded cache hits | 7.0 | 6.9 | 12.3 | 1.6 |
| Ablation: laptop timeline, time-scaled | 21.9 | 19.8 | 28.2 | 11.4 |
| Laptop-fitted, no Xeon anchor | 285.8 | 271.9 | 295.2 | 248.5 |

Per-call TPOT MAPE for the oracle is 6.4 %. High-load p95 by model, oracle
vs baseline: 1B 19.0 vs 50.6, 8B 12.7 vs 41.7, MoE 5.0 vs 85.0.

### Pre-registered criteria (`PREREG.md`)

| | Criterion | Result |
|---|---|---|
| C1 | p50 <= 25 %, p95 <= 30 %, TPOT <= 20 % | **pass** (7.0 / 6.9 / 6.4) |
| C2 | high-load p95 <= 0.5x baseline | **pass** (12.2 vs 59.1 = 0.21x) |
| C2 | no large win at low load | pass by its formula (1.6 vs 6.2, within 5 points). The oracle is still about 4x better at low load. Most of that comes from the baseline scaling TTFT linearly, which misses attention's quadratic term and uses stale laptop cache hits. |
| C3 | solo pricing >= 1.5x worse | **pass** (4.8x) |
| C3 | recorded cache hits worse | **pass by the letter only** (12.3 vs 12.2). On this grid, recomputing the cache does no work: both caches are large enough that the shared system prompt always hits. |
| C3 | time-scaled laptop timeline worse | **pass** (28.2 vs 12.2) |
| C4 | laptop transfer p50 <= 25 % | **fail, as predicted** (286 %). The transfer claim is dropped. |
| C5 | band covers truth p95 in >= 80 % of cells | pass when pooled (89.6 %) **but 79.2 % at high load**, just under 80 % in the regime that matters. Low load covers 100 %. |
| C6 | break point | see the stress table |

**What does the work.** The solo-priced ablation is indistinguishable from
the fair baseline (59.0 vs 59.1). The per-call phase-separated roofline alone
adds almost nothing over anchor+ratio. The win comes from the
continuous-batching replay, plus dependency-driven timing (the time-scaled
laptop timeline costs 16 points). This answers the refuter's narrow question:
the phase model matters only as the cost function inside the batching replay.

**Stress (C6)**: 8B, react + fan-out, high load, 4 seeds per level. The
strength of the unmodelled compute-saturation knee, NUMA loss and overlap
loss is scaled by the stress factor.

| stress | oracle p50 | oracle p95 | baseline p95 | per-call TPOT |
|---|---|---|---|---|
| 1x | 13.1 | 12.6 | 40.4 | 11.5 |
| 2x | 23.2 | 23.6 | 48.2 | 20.3 |
| 4x | 40.5 | 39.7 | 59.4 | 35.5 |
| 8x | 51.2 | 48.8 | 67.4 | 43.8 |

C1 breaks between 2x and 4x for task latency, and at 2x for per-call TPOT.
The oracle stays ahead of the baseline at every level.

**Probes beyond the grid**: 8B, react + fan-out, high load, 4 seeds each.
Values are p95 MAPE.

| probe | oracle | baseline | solo | rec. cache | timeline |
|---|---|---|---|---|---|
| oracle told 32/2048 batching, server runs 16/512 | 24.2 | 52.7 | 52.6 | 24.5 | 41.3 |
| prefix caching off on the Xeon | 8.4 | 66.1 | 64.0 | **48.5** | 30.9 |
| 6k-token Xeon prefix cache | 14.9 | 56.1 | 54.6 | **32.7** | 36.2 |

Recomputing the cache earns its place once the target engine's cache differs
from the laptop's. The deployment's batching flags must be known: getting
them wrong doubles the error.

**Worst cells** are 1B fan-out at high load, with 38 to 45 % p95 error.
Ablating the truth world on four of these cells:

| truth-world change | oracle error |
|---|---|
| none | 38-45 % |
| per-sequence sampler cost set to 0 | 6-23 % |
| NUMA loss set to 0 | 31-40 % |
| step noise set to 0 | 35-43 % |
| front-end delay set to 0 | 39-45 % |

The oracle has no per-sequence cost term, and that term is largest relative
to a 1B model's short step. The fix is to fit a per-sequence term from a
batched decode anchor and keep a separate shape held out. It is NOT applied
here because it was found after the grid ran. It needs its own
pre-registration.

### Probing the sim itself (does it grant the win?)

* **Two implementations, one answer.** With every unmodelled effect switched
  off, `truth_sim` and the oracle agree to 1e-6 on all three trace families
  (`test_two_implementations_agree_in_linear_limit`). This checks the
  scheduler, cache and DAG code, not the physics.
* **No god's-eye state.** `slo_oracle.py` imports only `cards.py` (checked by
  AST in the tests). Truth parameters reach it only through the anchor
  numbers. Different truth worlds give different anchors, and so different
  predictions.
* **Mutation check.** The tests kill each of six single-line mutants:
  - weights re-read per sequence;
  - cache off;
  - KV reads dropped;
  - dependencies ignored;
  - step overhead dropped;
  - sum instead of max.
* **Parameter perturbation**: 8 seeds per cell, the stress sweep, and the
  probes above.
* **Development runs, disclosed.** Before the grid, four quick runs used 2
  seeds and only 8B react.
  1. The first showed the truth world made batch-1 decode *compute*-bound.
     The saturation knee was applied even at n=1, which contradicts CPU
     decode being bandwidth-bound. Fix: an AVX-512 floor was added to the
     truth world.
  2. The second exposed a non-identifiable fit. The first anchor set used a
     16-token prefill to isolate overhead, but on a CPU that prefill is
     dominated by streaming the weights. The fitted overhead absorbed
     0.14 s and bandwidth efficiency hit its bound. Fix: the oracle's anchors
     changed to the two-context decode pair, and the baseline was given the
     same TPOT-vs-context interpolation.
  3. The third and fourth quick runs gave the numbers that motivated the
     probes, which the fourth added.
  The full grid was run once, after these fixes.
* **What the sim cannot show.** Truth and oracle share the FLOP/byte
  accounting and the vLLM-style scheduling policy. The sim therefore tests
  whether the mechanism survives unmodelled second-order effects. It does not
  test whether real oneDNN/IPEX/vLLM-CPU behaviour fits this cost structure.
  Only the live probes below can answer that.

## Live probes (not run: live benchmarks are in progress)

On this host (i9-13900T, 8P+16E, UHD 770, 2 NVIDIA GPUs; no AMX or DSA).
This checks the batching replay and the fit against a real engine. It does
NOT check Xeon accuracy:

1. Pin a vLLM CPU server to the P-core balloon (`k3d-gpu.io/cores=performance`)
   with `--max-num-seqs 16 --max-num-batched-tokens 512 --enable-prefix-caching`
   and `--enable-prompt-tokens-details`. Use `$IMAGE` = a pinned vLLM CPU
   image tag, and Llama-3.2-1B in bf16.
2. Run the four shapes from `slo_oracle.py anchors` (3 repeats each). Write
   `anchors.json` with the medians. Use the `i9-13900t` card.
3. Drive `gen_trace react|fanout|rag` (low: 8 tasks sequential; high: 24
   tasks, Poisson 0.5/s) through a DAG driver that sends each LLM step when
   its dependencies finish and sleeps for each tool step. That driver is the
   piece still missing. The agent-trace bench's runner is the natural home
   for it. Record per-task latency.
4. Score with the `PREREG.md` criteria. Also check `cached_tokens` from the
   server against the oracle's recomputed hits.
5. Repeat step 1 with `--max-num-seqs 4` but tell the oracle 16. This
   reproduces the sched-mismatch probe on real hardware.

On AWS c8i.48xlarge, which is what the claim is about:

6. STREAM triad, pinned per NUMA node, to replace the placeholder `mem_bw`.
   A oneDNN `benchdnn` bf16 matmul, to replace `peak_flops`.
7. Steps 2 to 4 for llama-3.2-1b, llama-3.1-8b and qwen3-30b-a3b, using the
   same engine flags, 8 repeats per (model, family, load). Success = the
   PREREG.md C1, C2 and C5 thresholds against measured latency.
8. Transfer re-check: fit anchors on the host (step 2) and on the c8i
   (step 7) for all three models. The laptop transfer claim comes back only
   if a laptop-only fit predicts c8i task p50 within 25 %.

## Provenance

* **Known (prior art):**
  - per-op roofline with efficiency factors, including CPU platform cards
    (GenZ-LLM-Analyzer README);
  - calibrated roofline transferred to unseen hardware, GPU only
    (KernelSight-LM, arXiv 2606.28565);
  - iteration-level serving simulation (Vidur, arXiv 2405.05465, confirmed in
    this session's scholar search; LLMServingSim);
  - agentic DAG trace replay, measured rather than predicted (XPerf, arXiv
    2608.20370; kubernetes-sigs inference-perf OTel replay);
  - a CPU bandwidth performance model for MoE (MoE-Lens);
  - regressing TPOT on context length, which is standard practice.
* **No prior art found in the searches logged for this idea** (scholar
  engines through searxng, GitHub repo search, abstract fetches; listed in
  the task's provenance log, plus three scholar queries this session):
  - the combination of anchor-only Xeon calibration, continuous-batching
    replay of an engine-agnostic agent DAG with prefix hits recomputed per
    target engine, and the result as a Kubernetes pre-promotion annotation
    gate with a held-out-residual error band;
  - no Kubernetes SLO gate built on predicted agent-task latency was found.
* **Unsearched:**
  - patents (the Google Patents page needs JS);
  - GitHub code search (HTTP 403);
  - Exa (rate-limited);
  - the arXiv API (HTTP 429);
  - Vidur's or LLMServingSim's support for agentic DAGs or CPU targets
    (their docs were not read);
  - the c8i.48xlarge per-size spec table (the AWS page extract had none).

  The novelty lies in the integration, so the obviousness risk is high.
